Inicio (main): main.cpp recibe argv[1] (ruta de config),
crea std::vector<Server> servers y pasa ese vector a Parser(argv[1], servers) para poblarlo. 
Luego usa ServerSocket::createListeners(servers) para abrir listeners y obtiene pollfds para el bucle de eventos. 
Finalmente llama a runEventLoop(...).

Parser y vector servers: Parser.cpp tokeniza y valida default.conf,
crea N instancias Server (clase definida en Server.hpp / Server.cpp) y rellena su ServerConfig:

	listen (multimap ip→puerto),
	root, index, autoindex,
	cgi (map extensión → intérprete/ejecutable),
	error_pages,
	locations (vector de LocationConfig con overrides por path),
	allowed_methods, client_max_body_size.

El servers es un vector de objetos Server (copias) —
cada Server guarda su ServerConfig y un _fd asociado al listener creado más tarde.
Creación de listeners (ServerSocket): ServerSocket.cpp

createListeners(servers) recorre cada Server y cada pareja (ip,port) en ServerConfig::listen.
Llama getaddrinfo, socket(), setsockopt(SO_REUSEADDR), pone el socket en non-blocking (fcntl), bind() y listen().
Si tiene éxito: server.setFd(listen_fd), añade listen_fd a _listeners y un pollfd con POLLIN a _pollfds.
Mantiene _created para evitar duplicados y expone getPollfds() para inicializar el array usado por poll().
Estructuras principales en ejecución:

std::vector<struct pollfd> pollfds (listeners + clientes + fds CGI registrados).
std::vector<Client> clients (objetos que encapsulan estado por conexión).
std::map<int,int> cgiFdToClientIdx (mapea fd de pipe CGI → socket del cliente) gestionado por cgi_fds.cpp.

Bucle de eventos (event loop): event_loop.cpp

Llama poll(pollfds, ...) en bucle.
Si poll señala sigfd (señales), las maneja (stop, etc.).
Si POLLHUP en un fd, cierra y elimina (o reencamina a manejo CGI si corresponde).
Si POLLIN en un listener: handleListenerEvent:
acceptNewClient() (no bloqueante) → añade nuevo pollfd (POLLIN) y construye Client(servers[j], client_fd) asociándolo al Server cuya getFd() coincide con el listen_fd.
Client::setEnv(env), chargeHeader() y chargeBody() para intentar procesar petición ya en la aceptación.
Si header+body (o no-POST) ya listos: sendResponse() y, según si se ha enviado todo o arrancó un CGI, ajustar pollfd.events a POLLOUT o POLLIN / registrar fds CGI con maybeRegisterClientCgiFds.
Si POLLIN en un socket cliente: handleClientInEvent:
Localiza Client por fd; si header no listo → chargeHeader() (recv acumulando hasta "\r\n\r\n"),
 luego parseHeader() y setPath(); si header listo y es POST → chargeBody() (gestiona content-length y chunked).
Cuando cuerpo listo → sendResponse() y setea pollfd.events = POLLOUT.
Si POLLOUT en socket cliente: handlePollOutEvent → Client::sendResponse() / flushResponse() y si _isSent cierra y elimina cliente/pollfd.
Lectura y parseo (Client):

Client::chargeHeader() y Client::chargeBody() (client_parsing.cpp):
recv() non-blocking, acumula en _header hasta CRLFCRLF; valida tamaños (limit 8192 cabecera).
parseHeader() separa request-line (método, URI, protocolo), valida métodos permitidos frente a ServerConfig::allowed_methods, extrae Host: y procesa cabeceras como Content-Length / Transfer-Encoding: chunked.
checkContentLength() compara con client_max_body_size global o de Location.
chunkManagement() decodifica chunked y rellena _body.
setPath() y checkPathValidity() ([srcs/client/client_path.cpp]):
Aplica matching de LocationConfig (por prefijo), decide isLocation, aplica alias o root según la location, concatena ruta a filesystem (root + request_path), busca index files, decide isAutoindexResponse o 403/404, protege traversal fuera de root (isWithinRoot).
Generación de la respuesta (Client::sendResponse) — [srcs/client/client_response.cpp]:

Si _sendBuffer vacío arma respuesta según _status y método:
DELETE → handleDelete() intenta borrar fichero y devuelve 204 o error.
POST → si la extensión está en cgi → si body listo manda directamente o arranca CGI (ver abajo). Si no es CGI, abre/crea fichero y escribe cuerpo (201/200), setea Location si nuevo.
GET/HEAD → si es dir y autoindex → generateDirectoryListing(). Si extensión mapeada a CGI → arranca CGI o espera su resultado. Si fichero estático → loadContent().
Construye cabeceras (Content-Length, Content-Type, Connection: close) y concatena cuerpo a _sendBuffer.
flushResponse() hace send() repetido en loop hasta agotar buffer o EAGAIN; marca _isSent si buffer vacío.
CGI no bloqueante:

startCgiNonBlocking(scriptPath, interpreter) ([srcs/client/client_cgi.cpp]):
Crea pipes inpipe/outpipe, fork().
En el hijo: dup2 para stdin/stdout, chdir al directorio del script, monta argv (interpreter + script), construye child_envp con variables CGI (REQUEST_METHOD, CONTENT_LENGTH, SCRIPT_FILENAME, DOCUMENT_ROOT, QUERY_STRING, etc.) y execve.
En el padre: parentProcess() guarda CgiState con in_fd/out_fd, write_buf (body a escribir), pone fds en non-blocking; si buffer vacío cierra in_fd.
Registro de fds CGI: maybeRegisterClientCgiFds(pollfds, cgiFdToClientIdx, client) en [srcs/main/cgi_fds.cpp] registra in_fd para POLLOUT y out_fd para POLLIN, y añade mapeos cgiFdToClientIdx[fd] = clientSocket.
Evento CGI en event loop: si pollfd corresponde a fd registrado en cgiFdToClientIdx, handleCgiFdEvent en [srcs/main/event_loop.cpp] localiza cliente y llama Client::handleCgiFdEvent(fd, revents):
Si POLLOUT en in_fd escribe lo que queda de write_buf.
Si POLLIN en out_fd lee y acumula en _cgi.read_buf.
Si POLLHUP o error cierra fds y llama finalizeCgiIfDone().
finalizeCgiIfDone() espera al pid (waitpid), cuando CGI terminó parsea headers y body del output CGI, extrae Status: y Content-Type, asigna _body y _status, marca _isBodyReady y _cgi.finalized, cierra fds y llama sendResponse() para generar _sendBuffer.
Mapeos y sincronización entre pollfds y clients:

pollfds contiene listeners, sockets de cliente y fds de CGI; su tamaño cambia dinámicamente.
clients almacena Client con getClientFd() igual al socket cliente.
cgiFdToClientIdx (map fd→clientSock) permite cuando poll() señala un fd de pipe identificar a qué cliente pertenece y reenviar eventos a Client::handleCgiFdEvent.
Registro/descenso de fds CGI se realiza con registerCgiFd / unregisterCgiFds ([srcs/main/cgi_fds.cpp]) — responsable de mantener pollfds y el mapa consistentes.
Errores y límites:

Parser detecta duplicados en listen y errores sintácticos (lanza excepción abortando inicialización).
Muchos métodos asignan _status a códigos HTTP (400, 403, 404, 405, 411, 413, 500, 505…) y sendResponse() usa _status para formar la respuesta.
checkContentLength() y límites en Location/Server evitan sobrepasar client_max_body_size.
Notas de diseño relevantes:

Client tiene muchas responsabilidades (parseo, CGI, IO, respuestas). El Server se guarda como copia dentro de Client (_listener), lo que simplifica gestión de ownership pero incrementa coste/copia.
Uso de poll() con fds variables y un mapa para fds CGI es una solución simple y explícita para multiplexar sockets de cliente y pipes CGI en un solo loop.
Se manejan ficheros en blocking para lectura/creación, pero los sockets y pipes son non-blocking; send()/recv() se usan con lógica de reintento/EAGAIN.
